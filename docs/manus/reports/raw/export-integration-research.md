# SpecFlow AI Export Integration Research

**Date**: May 15, 2026  
**Status**: Complete  
**Scope**: Jira Cloud and GitHub issue export integration behavior, field mappings, auth/security risks, UX state model, error handling

---

## Executive Summary

This research document provides comprehensive guidance for implementing Jira Cloud and GitHub issue export functionality in SpecFlow AI. The research covers API capabilities, field mapping strategies, authentication and security risks, export UX state models, error handling patterns, and product requirements.

**Key Findings**:
- **Jira Cloud API**: Supports issue creation via REST API v3 with flexible field mapping, custom fields, and bulk operations
- **GitHub API**: Supports issue creation with title, body, labels, assignees, and milestone fields; limited custom field support
- **Field Mapping**: SpecFlow AI artifacts (stories, epics, acceptance criteria) map naturally to Jira issue types and GitHub issue body structure
- **Auth Risks**: Token storage, permission scope validation, and workspace boundary enforcement are critical
- **Export UX**: Preview, dry-run, audit trail, and retry mechanisms are essential for user confidence
- **Error Handling**: Network failures, permission errors, and rate limiting require graceful degradation and user-facing recovery

**Highest-Priority Recommendations**:
1. Implement export preview with dry-run capability
2. Design robust token storage with encryption and scope validation
3. Create comprehensive error recovery UI with retry logic
4. Implement audit trail for export history and traceability
5. Design workspace boundary enforcement to prevent cross-workspace exports

## Jira Cloud Integration Research

### Jira Cloud REST API v3 Overview

**Source**: [Jira Cloud REST API v3 Documentation](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/)

Jira Cloud provides a comprehensive REST API for issue management. Key capabilities:

- **Issue Creation**: POST `/rest/api/3/issue` - Create single issues with fields
- **Bulk Issue Creation**: POST `/rest/api/3/issue/bulk` - Create multiple issues in one request
- **Issue Update**: PUT `/rest/api/3/issue/{issueIdOrKey}` - Update existing issues
- **Field Metadata**: GET `/rest/api/3/issue/createmeta` - Get available fields for issue creation
- **Custom Fields**: Support for custom field types (text, select, date, etc.)
- **Issue Linking**: Support for issue links and parent-child relationships

**API Authentication**:
- OAuth 2.0 with scopes: `write:jira-work`, `read:jira-work`
- API token authentication (email + API token)
- Workspace-scoped permissions

### Jira Issue Creation Request Structure

**Endpoint**: `POST /rest/api/3/issue`

**Required Fields**:
```json
{
  "fields": {
    "project": {
      "id": "10000"  // Project ID (required)
    },
    "issuetype": {
      "id": "10001"  // Issue type ID: Story, Epic, Bug, etc. (required)
    },
    "summary": "Feature title",  // Issue title (required)
    "description": {
      "type": "doc",
      "version": 1,
      "content": [
        {
          "type": "paragraph",
          "content": [
            {
              "type": "text",
              "text": "Issue description in Atlassian Document Format"
            }
          ]
        }
      ]
    }
  }
}
```

**Optional Fields**:
- `assignee` - User assignment (by account ID)
- `labels` - String array of labels
- `components` - Component IDs
- `fixVersions` - Version IDs
- `priority` - Priority level
- `duedate` - Due date (YYYY-MM-DD format)
- `customfield_*` - Custom fields (field-specific format)
- `parent` - Parent issue key (for subtasks)

**Response**:
```json
{
  "id": "10000",
  "key": "ED-24",
  "self": "https://your-domain.atlassian.net/rest/api/3/issue/10000"
}
```

### Jira Field Mapping Recommendations

| SpecFlow AI Field | Jira Field | Data Type | Notes |
| :--- | :--- | :--- | :--- |
| Story Title | `summary` | String (255 chars max) | Required, user-facing title |
| Story Description | `description` | ADF (Atlassian Document Format) | Supports rich text, code blocks |
| Acceptance Criteria | `description` (appended) or custom field | ADF or text | Can be part of description or separate custom field |
| Effort Estimate | `timetracking.originalEstimate` | String (e.g., "8h", "5d") | Optional, Jira format |
| Labels | `labels` | String array | Direct mapping, no transformation needed |
| Component | `components` | ID array | Map SpecFlow AI component to Jira component ID |
| Priority | `priority` | ID | Map SpecFlow AI priority (Low/Medium/High) to Jira priority ID |
| Quality Warnings | Comments (via POST `/rest/api/3/issue/{key}/comments`) | String | Create as separate comments after issue creation |
| Technical Notes | `description` (appended) or custom field | ADF or text | Can be part of description or separate field |

### Jira Error States & Recovery

**Common Error Responses**:

| Status Code | Error | Cause | Recovery |
| :--- | :--- | :--- | :--- |
| **400** | Bad Request | Invalid field format or missing required field | Validate field format, retry with corrected data |
| **401** | Unauthorized | Invalid or expired token | Prompt user to re-authenticate, refresh token |
| **403** | Forbidden | Insufficient permissions (no "Create issues" permission) | Show permission error, suggest admin contact |
| **404** | Not Found | Project ID or issue type ID invalid | Validate project/issue type exists, show error |
| **429** | Rate Limited | Too many requests (Jira rate limit exceeded) | Implement exponential backoff, queue requests |
| **503** | Service Unavailable | Jira service temporarily down | Retry with exponential backoff, show status message |

**Retry Strategy**:
- Implement exponential backoff (1s, 2s, 4s, 8s, 16s max)
- Retry on 429 (rate limit) and 503 (service unavailable)
- Do not retry on 400, 401, 403, 404 (client errors)
- Maximum 3 retries before showing error to user

### Jira Authentication & Security Risks

**Risk 1: Token Storage & Exposure**

**Risk**: API tokens stored in plaintext or transmitted insecurely

**Mitigation**:
- Store tokens encrypted in database (AES-256)
- Use environment variables for production secrets
- Transmit tokens only over HTTPS
- Implement token rotation policy (e.g., 90-day expiration)
- Never log or display tokens in UI

**Risk 2: Permission Scope Validation**

**Risk**: User exports to Jira project they don't have permission to access

**Mitigation**:
- Validate user permissions before export (GET `/rest/api/3/projects`)
- Check "Create issues" permission for target project
- Show permission error if validation fails
- Implement permission caching with TTL (5 minutes)

**Risk 3: Workspace Boundary Violation**

**Risk**: User exports SpecFlow AI project to wrong Jira workspace

**Mitigation**:
- Store Jira workspace ID with export configuration
- Validate workspace ID matches on each export
- Prevent cross-workspace exports
- Show workspace name in export preview

**Risk 4: Token Revocation & Disconnection**

**Risk**: User revokes Jira token but SpecFlow AI still tries to export

**Mitigation**:
- Implement token validation before export
- Gracefully handle 401 (Unauthorized) responses
- Prompt user to re-authenticate if token invalid
- Implement "Disconnect" button to clear stored credentials

## GitHub Integration Research

### GitHub REST API Overview

**Source**: [GitHub REST API Documentation](https://docs.github.com/rest/issues)

GitHub provides REST API for issue management. Key capabilities:

- **Issue Creation**: POST `/repos/{owner}/{repo}/issues` - Create single issues
- **Issue Update**: PATCH `/repos/{owner}/{repo}/issues/{issue_number}` - Update existing issues
- **Labels**: GET/POST `/repos/{owner}/{repo}/labels` - Manage labels
- **Assignees**: PATCH `/repos/{owner}/{repo}/issues/{issue_number}/assignees` - Assign users
- **Milestones**: GET/POST `/repos/{owner}/{repo}/milestones` - Manage milestones
- **Comments**: POST `/repos/{owner}/{repo}/issues/{issue_number}/comments` - Add comments

**API Authentication**:
- OAuth 2.0 with scopes: `repo` (full repo access) or `issues` (issues only)
- Personal access tokens
- GitHub App tokens

### GitHub Field Mapping Recommendations

| SpecFlow AI Field | GitHub Field | Data Type | Notes |
| :--- | :--- | :--- | :--- |
| Story Title | `title` | String (max 256 chars) | Required, user-facing title |
| Story Description | `body` | Markdown string | Optional, supports Markdown formatting |

| Technical Notes | `body` (appended) | Markdown string | Can be part of body or separate section |

### GitHub Error States & Recovery

**Common Error Responses**:

| Status Code | Error | Cause | Recovery |
| :--- | :--- | :--- | :--- |
| **400** | Bad Request | Invalid field format or invalid label | Validate field format, create missing labels |
| **401** | Unauthorized | Invalid or expired token | Prompt user to re-authenticate |
| **403** | Forbidden | Rate limit exceeded or insufficient permissions | Implement backoff, suggest retry later |
| **404** | Not Found | Repository not found or user not found | Validate repo/user exists, show error |
| **422** | Unprocessable Entity | Invalid assignee or milestone | Validate assignees/milestones exist |
| **503** | Service Unavailable | GitHub service temporarily down | Retry with exponential backoff |

**Retry Strategy**:
- Implement exponential backoff (1s, 2s, 4s, 8s, 16s max)
- Retry on 403 (rate limit), 422 (validation), and 503 (service unavailable)
- Do not retry on 400, 401, 404 (client errors)
- Maximum 3 retries before showing error to user

### GitHub Authentication & Security Risks

**Risk 1: Token Storage & Scope Validation**

**Risk**: Overly broad token permissions or insecure storage

**Mitigation**:
- Request minimal scopes (e.g., `issues` instead of `repo`)
- Store tokens encrypted in database (AES-256)
- Validate token scopes before export
- Implement token rotation policy

**Risk 2: Repository Access Validation**

**Risk**: User exports to repository they don't have permission to access

**Mitigation**:
- Validate user has push access to repository (GET `/repos/{owner}/{repo}`)
- Check "issues" permission for target repository
- Show permission error if validation fails
- Implement permission caching with TTL (5 minutes)

**Risk 3: Workspace/Organization Boundary**

**Risk**: User exports to wrong organization or repository

**Mitigation**:
- Store repository owner and name with export configuration
- Validate repository owner matches on each export
- Prevent cross-organization exports
- Show repository name in export preview

**Risk 4: Rate Limiting & API Quota**

**Risk**: Bulk exports hit GitHub API rate limits (60 requests/hour unauthenticated, 5000/hour authenticated)

**Mitigation**:
- Implement request queuing and rate limiting on client side
- Check rate limit headers before export
- Implement exponential backoff on 403 responses
- Show rate limit status to user

**Purpose**: Validate export configuration without creating actual issues

   - All assignees exist in target system
   - All labels exist or can be created
3. System returns validation results:
   - ✓ All validations passed
   - ✗ Validation failed: [specific error]
4. User can proceed to export or fix issues

## Export UX State Model

### State Diagram

```
[Disconnected] 
    ↓ (Click "Connect Jira" or "Connect GitHub")
[Connecting] 
    ↓ (User authenticates)
[Connected] 
    ↓ (Click "Export")
[Validating] 
    ├─ (Validation failed) → [Error: Show error message, allow retry]
    └─ (Validation passed) → [Preview]
[Preview] 
    ├─ (Click "Cancel") → [Connected]
    └─ (Click "Export") → [Exporting]
[Exporting] 
    ├─ (Partial success) → [Partial Success: Show results, allow retry]
    ├─ (All succeeded) → [Success: Show results, links]
    └─ (All failed) → [Error: Show errors, allow retry]
[Success] 
    ├─ (Click "View in Jira/GitHub") → [Open external link]
    └─ (Click "Export Again") → [Connected]
[Partial Success] 
    ├─ (Click "Retry Failed") → [Exporting]
    └─ (Click "Done") → [Connected]
[Error] 
    ├─ (Click "Retry") → [Exporting]
    ├─ (Click "Disconnect") → [Disconnected]
    └─ (Click "Done") → [Connected]
```

### State Descriptions

| State | Description | User Actions | Next States |
| :--- | :--- | :--- | :--- |
| **Disconnected** | No integration configured | "Connect Jira", "Connect GitHub" | Connecting |
| **Connecting** | Authentication in progress | Wait for OAuth callback | Connected, Error |
| **Connected** | Integration ready, no export in progress | "Export", "Disconnect", "Test" | Validating, Disconnected |
| **Validating** | Checking export configuration | Wait for validation | Preview, Error |
| **Preview** | Showing export preview to user | "Export", "Cancel" | Exporting, Connected |
| **Exporting** | Export in progress | Wait for completion | Success, Partial Success, Error |
| **Success** | All stories exported successfully | "View in Jira/GitHub", "Export Again", "Done" | Connected |
| **Partial Success** | Some stories exported, some failed | "Retry Failed", "Done" | Exporting, Connected |
| **Error** | Export failed, user intervention needed | "Retry", "Disconnect", "Done" | Exporting, Disconnected, Connected |

## Error Recovery & Retry Behavior

### Error Recovery Flow

**Step 1: Error Occurs**
- Export fails (network error, permission error, rate limit, etc.)
- System captures error details and context

**Step 2: User Notification**
- Show error message with specific details
- Explain what went wrong and why
- Suggest recovery action

**Step 3: Retry Options**
- **Automatic Retry**: For transient errors (network, rate limit)
  - Implement exponential backoff (1s, 2s, 4s, 8s, 16s)
  - Maximum 3 retries
  - Show progress to user
- **Manual Retry**: For user-fixable errors (permission, token expired)
  - Show "Retry" button after user fixes issue
  - Allow user to re-authenticate if needed
  - Show "Disconnect" button to clear configuration

**Step 4: Partial Success Handling**
- If some stories export successfully and some fail:
  - Show which stories succeeded (with links)
  - Show which stories failed (with error details)
  - Allow user to retry only failed stories
  - Prevent re-exporting successful stories

### Error Messages & Recovery Suggestions

| Error | Message | Recovery |
| :--- | :--- | :--- |
| **Network Error** | "Connection failed. Please check your internet connection and try again." | Automatic retry with backoff |
| **Token Expired** | "Your Jira/GitHub connection has expired. Please reconnect." | "Reconnect" button → OAuth flow |
| **Permission Denied** | "You don't have permission to create issues in this project. Contact your admin." | "Disconnect" button, suggest admin contact |
| **Rate Limited** | "Too many requests. Please wait a few minutes and try again." | Automatic retry with longer backoff |
| **Invalid Project** | "Project 'MY-PROJECT' not found. Please verify the project ID." | "Validate" button → Check project exists |
| **Invalid Assignee** | "User 'john.doe' not found in target project. Please update assignees." | Show assignee picker, allow update |
| **Service Unavailable** | "Jira/GitHub is temporarily unavailable. Please try again later." | Automatic retry with backoff |

## Product Requirements for Codex Implementation

### PR-001: Export Configuration UI

**Objective**: Allow users to configure export targets and field mappings

**Scope**:
- Add "Export Settings" page or modal
- Support Jira Cloud and GitHub as export targets
